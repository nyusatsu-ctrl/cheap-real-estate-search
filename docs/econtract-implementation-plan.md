# 自社ローン電子契約 最終運用設計

## 目的とフロー

元の自社ローン顧客・審査管理システムを主画面として維持し、ローン可決後の電子契約を1回で完結させる。

1. 元システムでプレミアまたはアストの可決を確認
2. 「電子契約」ボタンで顧客・申込情報を契約管理へ同期
3. 同一の申込管理番号または元行キーの既存候補があれば、その契約を開く
4. 管理者が契約管理画面で内容とメールアドレスを確認
5. 管理者が「電子契約をメール送信」を実行
6. 顧客が氏名確認、本文確認、9項目の個別同意、メールOTPを行って締結
7. 本文・顧客・同意・認証・IP・UA・時刻・hash・eventを証跡として保存

元システムのボタンは候補同期と確認画面表示だけを行い、電子契約レコードの発行やメール送信を行わない。

## 発行条件

次の3条件をすべて満たす場合だけ、候補同期・新規送信・再送を許可する。

- `contract_type = loan`
- `approval_status = approved`
- `finance_company = premium` または `ast`

画面表示、GASサーバー、候補同期API、管理者Server Actionの各境界で条件を再検証する。アプラス、審査中、否決、保証人条件、未審査はfail closedとする。

## 一段階契約

新規運用では `sales_econtracts.contract_kind = purchase_intent` だけを発行する。契約書の表示名は「電子契約」、正式タイトルは「自社ローン審査可決後 購入申込・手続継続確認契約書」とする。

従来の `vehicle_confirmation` 行は削除・変換せず、過去の電子契約証跡として閲覧専用で保持する。新規作成経路と送信・再送経路は設けない。

同一販売契約に締結済みの電子契約があれば、新しい電子契約は発行しない。未締結契約の再送では、本文・顧客・条件snapshotを変更せず、専用URLの世代だけを更新し、旧アクセスセッションと未完了OTPを無効化する。

## 候補同期と重複防止

候補同期は次の情報だけをホワイトリスト方式で受け取る。

- 氏名、フリガナ、電話、メール、住所
- 車・バイク区分、希望車種
- 信販会社、審査結果
- 申込管理番号、元システム行キー、行番号、受信日時

APIは既存の元システム連携secretをサーバー間で検証し、電子契約feature gateが無効なら404とする。DB関数は1トランザクションで既存候補を検索し、なければ顧客、販売契約候補、車両、ローン、auditを作成する。元行キー・行番号の部分一意indexと申込番号・行キーのtransaction advisory lockにより、連打や並行実行でも重複を防ぐ。

## 証跡と不変性

- URL tokenは256-bit乱数とし、DBにはSHA-256 hashだけを保存する。
- 氏名一致後にHttpOnly / Secure / SameSite=Strictの短時間アクセスセッションを作る。
- OTPはkeyed hash、有効期限、試行回数、再送間隔、1時間上限を持ち、平文を保存しない。
- 署名には同一アクセスセッションのOTP認証と9項目すべての個別同意を必須とする。
- 契約本文、顧客、ローン申込、条件、重要事項のsnapshotは発行後変更禁止とする。
- 締結後の契約行と認証済みverificationは変更・削除禁止、eventは追記専用とする。
- 電子契約4テーブルはRLSとFORCE RLSを有効にし、ブラウザロールの表アクセスを許可しない。

## 状態表示

DB状態とURL期限から、管理画面では次を表示する。

- `draft`: 未送信
- `sent`: 送信済み
- `opened`: 本人確認／OTP待ち
- `verified`: 契約締結待ち
- `signed`: 締結済み
- `cancelled`: 取消済
- 未締結かつ専用URL期限超過: 期限切れ

## 機能ゲート

`ECONTRACT_ENABLED` が文字列 `true` で、次の4項目がすべて存在する場合だけ有効にする。

- `ECONTRACT_BASE_URL`
- `ECONTRACT_RESEND_API_KEY`
- `ECONTRACT_EMAIL_FROM`
- `ECONTRACT_OTP_PEPPER`

診断用や一般URLへのfallbackは設けない。Previewでは無効を維持し、Productionの既存値はリリース作業で変更しない。

## リリース検証

- 対象／対象外の信販会社・審査状態を自動テスト
- 候補同期だけでは電子契約・メールが生成されないことを確認
- 同一申込の同期が冪等であることをmigrationとテストで確認
- 旧種別の新規発行経路がないことを確認
- 正式本文、9同意、OTP、署名条件、不変性を確認
- 契約ログインのヘッダー、title、description、OG、Twitterを確認
- 診断、GPS、既存機能の回帰テスト
- typecheck、lint、関連テスト、build、Preview、Production Readyを確認

実顧客データ、実メール、実署名を使った確認は行わない。
